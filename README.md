# Транзакции: Kafka → ClickHouse

Загрузка CSV в Kafka и поиск категории самой крупной транзакции по каждому штату.

```text
train.csv + test.csv → produce.py → Kafka (transactions, 3 партиции)
                                      ↓
                        ClickHouse Kafka Engine
                                      ↓ materialized view
                        MergeTree + проекция state_max
                                      ↓
                        max_transaction_by_state.csv
```

## Данные и постановка

Источник: [данные задания на Kaggle](https://www.kaggle.com/t/1918f3f6435300327d38d6c596f97394).
Скачанные файлы нужно положить в `data/`:

```text
data/
  train.csv
  test.csv
```

В `train.csv` 786 431 транзакция, в `test.csv` 262 144. Используются оба файла:
всего 1 048 575 строк, 51 значение `us_state` (включая DC), 14 категорий.
`sample_submition.csv` содержит шаблон предсказаний, поэтому не загружается.
В test нет `target`: в таблице это `NULL`, а не 0. Все остальные исходные поля сохраняются.
Время в CSV без часового пояса; для хранения используется единая условная зона UTC,
без попытки восстановить местное время штатов. На максимум суммы это не влияет.

Под наибольшей транзакцией понимается максимальный `amount`, а не сумма расходов
по категории. При равенстве сумм выбирается лексикографически наибольшая категория:
это делает ответ однозначным. `max_amount` оставлен в результате для проверки.
Пункты 2 и 3 задания повторяют один запрос — он находится в одном SQL-файле.

## Запуск

Нужны Docker Engine/Desktop и Docker Compose v2 с поддержкой `--wait`.
Для Docker достаточно выделить 4 CPU, 6 ГБ RAM и примерно 5 ГБ свободного диска.
На macOS также подходит Colima (`colima start --cpu 4 --memory 6`).
Python на хосте не нужен: скрипты запускаются в контейнере.

```bash
git clone https://github.com/chega8/sys_design_hse.git
cd sys_design_hse
mkdir -p data results
# Положите train.csv и test.csv в data/.
docker compose build loader
docker compose up -d --wait
docker compose run --rm --no-deps loader
```

Последняя команда запускает отдельный скрипт `scripts/produce.py`. Он читает CSV
построчно, формирует JSONEachRow и дожидается подтверждения доставки всех сообщений
от Kafka. Ошибки чтения и доставки приводят к ненулевому коду завершения.
Поля с запятыми читаются через `csv.DictReader`, деньги передаются строкой в Decimal,
почтовые индексы сохраняются строками вместе с ведущими нулями.

DDL из `sql/01_schema.sql` выполняется при первом создании ClickHouse.
Сначала создаётся топик, затем Kafka-таблица, целевая таблица и materialized view.
Проверки готовности в Compose исключают запуск загрузки до создания таблиц.
Пароли `student/student` предназначены для локального учебного стенда;
HTTP-порт ClickHouse открыт только на `127.0.0.1:8123`, Kafka доступна внутри сети Compose.

## Проверка и получение CSV

```bash
docker compose run --rm --no-deps loader python -m unittest discover -s tests -v
docker compose run --rm --no-deps loader python scripts/verify_export.py /data/train.csv /data/test.csv
```

Проверка ждёт попадания всех строк в ClickHouse (до 300 секунд), сверяет количество
по файлам и уникальность `(source_file, source_row)`, независимо рассчитывает максимумы
по исходным CSV и сравнивает их с SQL. Дополнительно сравниваются ответы с включённой
и выключенной проекцией. При несовпадении скрипт завершается с ошибкой.

Результат **самого SQL-запроса из ClickHouse** сохраняется в
`results/max_transaction_by_state.csv`, отчёт проверки — в `results/validation.json`.
Эти файлы входят в репозиторий. Исходные данные исключены через `.gitignore`
и не попадают в Docker-образ благодаря `.dockerignore`.

Запрос можно выполнить отдельно:

```bash
docker compose exec -T clickhouse clickhouse-client --user student --password student \
  --queries-file /dev/stdin < sql/02_max_transaction.sql > results/max_transaction_by_state.csv
```

`argMax(cat_id, tuple(amount, cat_id))` выбирает категорию строки с максимальной
парой «сумма, категория». Поэтому правило разрешения одинаковых сумм совпадает
в SQL и независимой проверке. `Decimal(18, 2)` исключает погрешности float для денег.

## Оптимизация хранения

`sql/00_baseline.sql` содержит исходный вариант: MergeTree с `ORDER BY tuple()`,
обычными строками и стандартным сжатием. Финальный DDL — `sql/01_schema.sql`:

- `LowCardinality(String)` для повторяющихся штатов, категорий, городов, профессий,
  продавцов и имён файлов; `UInt32` для населения, `Nullable(UInt8)` для метки.
- `ZSTD(1)` для строк и сумм, `Delta + ZSTD(1)` для времени и номера исходной строки.
- Сортировка `(us_state, transaction_time)` группирует записи одного штата и близкое время.
- Агрегатная проекция `state_max` хранит состояния `argMax` и `max` по штатам.
  ClickHouse поддерживает её при вставках и выбирает при выполнении исходного запроса.

Главное ускорение этого запроса даёт проекция: вместо всех транзакций читаются
агрегаты по штатам из частей таблицы. Одна сортировка не позволяет пропустить
весь набор при `GROUP BY` без фильтра. Проекция требует дополнительного места
и работы при вставках; она полезна именно для данного запроса.
Разбиения по месяцам нет: запрос охватывает все даты, а объём небольшой.

Для существующей таблицы недостаточно отредактировать CREATE TABLE IF NOT EXISTS:
он не меняет уже созданную схему. В этом проекте финальный DDL применяется на чистом
томе. При миграции работающего стенда потребовались бы ALTER и материализация
проекции для старых частей.

## Сравнение вариантов

После полной загрузки и проверки:

```bash
docker compose run --rm --no-deps loader python scripts/benchmark.py
```

Скрипт пересоздаёт содержимое отдельной `transactions_baseline` из загруженных
данных, объединяет части обеих таблиц для сопоставимого замера и сравнивает:
исходную таблицу, оптимизированную без проекции и оптимизированную с проекцией.
Это три режима одного запроса, результаты должны совпасть.

В каждом режиме два прогрева, затем семь измерений; один поток, query cache
выключен. Время HTTP-вызова записывается отдельно от серверных метрик
`system.query_log`. Сохраняются прочитанные строки и байты, память и использованные
проекции. Скрипт проверяет, что оптимизатор действительно выбрал `state_max`.

Результат запуска на macOS/Apple Silicon, Colima (4 CPU, 6 ГБ RAM),
ClickHouse 25.3.3.42, 1 048 575 строк:

| Вариант | Медиана HTTP, мс | Медиана сервера, мс | Прочитано строк | Прочитано байт |
|---|---:|---:|---:|---:|
| Исходная таблица | 67.789 | 66 | 1 048 575 | 40 396 855 |
| Оптимизированная, проекция выключена | 61.653 | 60 | 1 048 575 | 10 485 750 |
| Оптимизированная, проекция включена | 2.293 | 1 | 51 | 8 781 |

Медиана HTTP-времени сократилась примерно в 29.6 раза. Серверное время округлено
до миллисекунд, поэтому для короткого запроса оно менее точно. Размах HTTP-времени
по семи повторам: 1.907, 11.759 и 1.729 мс соответственно. Без проекции уменьшился
объём чтения благодаря словарному представлению строк, но полного сканирования
избежать не удалось. План и `system.query_log.projections` подтверждают использование
`state_max` в третьем варианте. Все ответы совпали.

Объём активных частей на диске: 71 783 555 байт у исходной таблицы и
45 559 203 байта у оптимизированной (примерно на 36.5% меньше). Проекция занимает
1 233 байта после слияния частей, её размер входит в общий `bytes_on_disk` таблицы.
Размеры не включают Kafka, логи ClickHouse и служебные данные Docker; baseline
хранится отдельно только ради сравнения и удваивает набор транзакций на стенде.

Файлы результатов:

- `results/benchmark.csv` — все повторы, без усреднения;
- `results/storage.csv` — активные части основной и исходной таблиц;
- `results/projection_storage.csv` — размер самой проекции;
- `results/explain.txt` — план оптимизированного запроса.

`OPTIMIZE FINAL` здесь нужен только для воспроизводимого сравнения на статическом
наборе, его не нужно запускать после каждой загрузки. Замеры выполняются на прогретых
данных и не характеризуют холодный диск или кластер под нагрузкой.

## Повторный запуск и диагностика

Остановка с сохранением данных:

```bash
docker compose down
```

После `docker compose up -d --wait` можно повторять проверку и benchmark.
**Не запускайте producer второй раз в тот же топик:** это повторно отправит CSV.
Idempotent producer защищает от повторов при сетевых retries в своей сессии,
но не от повторного запуска скрипта. Связка Kafka Engine → MergeTree работает
с доставкой как минимум один раз: при сбое на границе вставки и commit offsets
возможны дубликаты. Их обнаруживает проверка по исходному файлу и номеру строки.
Максимум устойчив к точным повторам, но количество строк — нет.

Чтобы начать загрузку заново, удалите **оба тома этого учебного проекта**:

```bash
docker compose down -v
docker compose up -d --wait
docker compose run --rm --no-deps loader
docker compose run --rm --no-deps loader python scripts/verify_export.py /data/train.csv /data/test.csv
```

`down -v` удаляет данные Kafka и ClickHouse. Файлы в `data/` и `results/` остаются.
Нельзя очищать только ClickHouse, оставив committed offsets Kafka: сообщения
не будут автоматически прочитаны заново.

```bash
docker compose ps -a
docker compose logs --tail=100 kafka clickhouse
docker compose exec -T clickhouse clickhouse-client --user student --password student \
  --query 'SELECT count() FROM homework.transactions'
```

При занятом порте 8123 измените левую часть проброса порта в Compose.
На первый запуск нужно время для скачивания образов. При изменении Python-кода
повторите `docker compose build loader`.

Если при сборке возникает `CERTIFICATE_VERIFY_FAILED` из-за сертификата вашей
сети, передайте доверенный PEM bundle через BuildKit secret:

```bash
CA_CERT_PATH=/absolute/path/to/ca-bundle.pem docker compose \
  -f docker-compose.yml -f docker-compose.ca.yml build loader
```

Сертификат используется только во время установки зависимостей и не сохраняется
в образе. В обычной сети достаточно стандартной команды сборки выше.
